### 1. Isolated user-mode network with `guestfwd` (run `restrict-on`, Ubuntu 26.04.1 live)

**Guest and method.** Ubuntu reference ISO (`lab/media/ubuntu-26.04.1-desktop-amd64.iso`, SHA-256 as in R2c-01), booted with the kernel and initrd extracted from the ISO (`tar -xf`, bsdtar) so that the console is the serial port: `-kernel casper/vmlinuz -initrd casper/initrd -append "boot=casper console=ttyS0,115200 systemd.unit=multi-user.target"`, `pc-q35`, `-accel whpx`, `-cpu Skylake-Client-v4`, 2 vCPU, 2 GiB, `-serial tcp:127.0.0.1:47001,server=on,wait=off`, process priority BelowNormal. Login `ubuntu` with empty password on `ttyS0`. Commands are typed through the serial line by a std-only helper (`lab/integration-spike/tools`, `spike serial`); guest scripts are pushed in base64 chunks and checked by SHA-256. Scripts: `lab/integration-spike/guest/nettest.py`, `multiconn.py`, `tput.py`; logs in `lab/integration-spike/logs/`.

NIC: `-nic user,model=e1000,restrict=on,guestfwd=tcp:10.0.2.100:7000-tcp:127.0.0.1:47010`. Host side: `spike listen 127.0.0.1:47010 req` (line protocol HELLO/SINK/SEND) and a decoy `spike listen 127.0.0.1:47021 banner` on the host loopback. **Semantics of `guestfwd` to a TCP chardev (decisive).** The chardev `tcp:127.0.0.1:47010` is a *client* opened **once, when QEMU starts** (host log: `accepted from 127.0.0.1:56131` at QEMU start, before the guest booted). Every later guest connection to `10.0.2.100:7000` is spliced onto that one host stream (`multiconn-loopback.txt`):

- sequential connections A then B: both answered, but on the same host connection (`seq` 2, 3 continue the counter of the first probe); the host never sees a guest connect or close;
- two concurrent connections C and D: D's request answered on D; **C's request answered on D** (`D got (after C) b'HI concC 5'`), C received nothing. Replies go to one guest socket regardless of which one sent the request.

So `guestfwd` to a chardev is a single byte pipe, not a TCP port forward. It cannot carry protocols that open several connections or rely on connection open/close (HTTP clients such as the WebDAV redirector, SQL Server TDS with connection pooling, WCF `net.tcp`). It fits a channel spoken by one guest component (LightVM Tools) with its own framing and multiplexing.

The probe of `nettest.py` repeated with these five rules present (`nettest-restrict-on-2.txt`) gives the same result as the first run: only the rule answers; host, LAN (including the LAN DNS server that is the target of rule 10.0.2.101 when addressed directly), Internet, UDP DNS and IPv6 refused or silent; only slirp's own gateway answers ICMP.

**Consequence for ADR-0033 (endpoint allowlist).** `guestfwd` cannot implement "guest 10.0.2.101:1433 â†’ SQL Server": the host side is one connection opened by QEMU at start, shared by every guest connection, with no open/close per connection; concurrent connections get each other's replies; a service that closes idle connections breaks the rule. Ways that give per-connection TCP to an approved endpoint, none verified here:

1. **Guest-side multiplexer in LightVM Tools**: the application connects to a local listener of the Tools in the guest (`127.0.0.1:1433`, or the virtual address added to the loopback); the Tools carry each connection as a framed stream over the single guestfwd channel; the supervisor opens the real host connection per stream, only to approved endpoints. Needs the Tools in the guest (so it is not "without guest software").
2. **Supervisor-owned user-mode network stack**: QEMU `-netdev stream` / `dgram` to a supervisor process that terminates guest TCP itself (the gvisor-tap-vsock/gvproxy model used by Podman on Windows) and opens host connections only to the allowlist. Per-connection semantics, DNS answered by the supervisor, no guest software. Needs a TCP/IP stack in the supervisor (e.g. smoltcp) and its own verification. `-netdev stream` support on this Windows build not checked.
3. **`hostfwd` is the opposite direction** (host â†’ guest) and does not apply.

**Other QEMU network back ends on this build.** `-netdev help` lists `socket`, `stream`, `dgram`, `hubport`, `tap`, `user`. QEMU started (`-S`, TCG, e1000 on the netdev) with `-netdev stream,server=on,addr.type=inet,addr.host=127.0.0.1,addr.port=47015` (listening on 127.0.0.1:47015), with `addr.type=unix,addr.path=<file>`, and with `-netdev dgram` on loopback UDP. So option 2 above is available on the Windows build at the QEMU level; no traffic was carried through it in this spike.

### 3. USB: `usb-host` (libusb/WinUSB) and `usb-redir` (usbredir/UsbDk)

**Bundled build.** QEMU 11.1.0 has both devices: `usb-host` and `usb-redir` (`-device help`), controllers `qemu-xhci`, `nec-usb-xhci`, `usb-ehci`, `ich9-usb-ehci1/2`, `ich9-usb-uhci1..6`, `piix3/piix4-usb-uhci`. DLLs: `libusb-1.0.dll` 1.0.30 (`FileVersion 1.0.30.12037`, libusb.info; contains the UsbDk backend strings), `libusbredirparser-1.dll`. QEMU's `hw/usb/host-libusb.c` never calls `libusb_set_option(..., LIBUSB_OPTION_USE_USBDK)`, so `usb-host` on Windows uses libusb's default WinUSB backend (devices bound to WinUSB, libusbK or libusb0); on Windows it polls libusb with a timer (10 ms with requests in flight, 1 s idle) and rescans devices every 2 s (source read on gitlab.com/qemu-project/qemu, `master`).

**Host state (read-only checks, 2026-10-15).** No UsbDk, usbipd, VBoxUSB/VBoxUSBMon, libusbK or libusb0 service; no upper filter on the USB class key; WinUSB (`WinUsb.sys`) running. Present devices include a **VIA Labs "USB 2.0 BILLBOARD" (`2109:0103`), already bound to the inbox `WINUSB` service** by the hub firmware's descriptors: it was used for the test below without installing anything.

**`usb-host` executed (run `usb`, Ubuntu live, `-device qemu-xhci,id=xhci -device usb-ehci,id=ehci`, log `usb-host-guest.txt`).**

### 4. Toolchain for the Windows tools on XP and Vista

**Installed on this host.** Rust 1.99.0 (pinned, `x86_64-pc-windows-msvc`) and stable `x86_64-pc-windows-gnu`; WinLibs GCC 16.1.0 `x86_64-w64-mingw32` **UCRT** only (no i686, and UCRT is not part of XP); MSVC 14.44 (VS 2022) and 14.51 (VS 18) with **x64-targeting compilers only** (`bin\Hostx64\x64`), VS 2019 without VC tools; no `v141_xp` platform toolset; Windows SDK 7.1A folder present (no compiler). So no 32-bit C compiler is available without installing one. For the spike the official Rust target `i686-pc-windows-msvc` was added to the pinned 1.99.0 toolchain (`rustup target add`, download verified by rustup; reversible with `rustup target remove`).

**Rust standard library: not usable before Windows 10.** A std hello world (thread, `SystemTime`, `TcpStream`, `read_dir`) built with Rust 1.99.0 `x86_64-pc-windows-gnu` imports, statically: `api-ms-win-core-synch-l1-2-0.dll` (`WaitOnAddress`, `WakeByAddressAll/Single`, Windows 8+), `bcryptprimitives.dll` (`ProcessPrng`), `GetSystemTimePreciseAsFileTime` (Windows 8+), the UCRT API sets `api-ms-win-crt-*` (not on XP), plus Vista-only `InitOnce*`, `CreateWaitableTimerExW`, `GetFinalPathNameByHandleW`, `CreateSymbolicLinkW` (`dumpbin /imports`). The loader fails before `main` on XP, Vista and 7. The tier-3 `*-win7-windows-msvc` targets need nightly `build-std` and still do not cover Vista/XP; old Rust releases are unmaintained and never supported XP in std.

**Rust `no_std` with `raw-dylib`: works, executed on the host.** `lab/integration-spike/toolchain/hello-nostd` (`#![no_std]`, `#![no_main]`, `panic = "abort"`, LTO): kernel32 functions declared with `#[link(name = "kernel32", kind = "raw-dylib", import_name_type = "undecorated")]` (no import library, no MSVC/SDK libraries needed), linked by `rust-lld` with `/SUBSYSTEM:CONSOLE,5.01 /ENTRY:mainCRTStartup /NODEFAULTLIB`; `memset`, `memcpy`, `memcmp` and `_fltused` defined in the program (core references them; without LTO it also needs `__aulldiv` and `__CxxFrameHandler3`). Result: `hello-nostd.exe`, 2 560 bytes, SHA-256 `BCAAF4D4…1470A31D`; PE machine x86, operating system and subsystem version **5.01**; imports only `kernel32.dll`: `ExitProcess`, `GetStdHandle`, `GetVersion`, `WriteFile`. Run on the host (WoW64): prints `LightVM Tools toolchain test (Rust no_std, raw-dylib): Windows 6.2 build 9200` (6.2 is the version Windows reports to a program without a compatibility manifest), exit 0. Pitfall found: without `import_name_type = "undecorated"` the x86 imports are stdcall-decorated (`_ExitProcess@4`) and the loader fails with `0xC0000139` (entry point not found).

Not executed: the binary in an XP or Vista guest (see section 6 for the Vista guest); a larger program (allocator over `HeapAlloc`, Winsock, clipboard, threads) in `no_std` + `alloc`.

**Options compared.**

| Option | XP/Vista | Cost and risk |
| --- | --- | --- |
| Rust `no_std` + `alloc`, Win32 through `raw-dylib` (or `windows-sys` in no_std), `rust-lld` | yes, the import table is exactly what the code declares; checkable in CI by listing imports against an allowlist of XP/Vista APIs | no std: own small wrappers for threads, sockets, files, allocator; same language as the rest of LightVM; stable toolchain; i686 target assumes SSE2 (every CPU model LightVM offers has it) |

**Recommendation:** Rust `no_std` + `alloc` with direct Win32 imports for the Windows tools (one binary per architecture: i686 subsystem 5.01, x86_64 subsystem 5.02 for XP x64/Vista+ x64), plus a CI check that the import table only contains functions present in XP SP3 (or Vista SP2 for features that need it, loaded dynamically with `GetProcAddress`). Linux tools can use std.

### 5. Shared folders through the Windows WebDAV redirector

**Spike server.** `spike dav ADDR ROOT [BASIC]` (`lab/integration-spike/tools/src/dav.rs`, std only): OPTIONS, PROPFIND (depth 0/1), GET/HEAD, PUT (Content-Length or chunked), DELETE, MKCOL, MOVE/COPY, PROPPATCH (accepts everything), LOCK/UNLOCK (fixed token); optional Basic authentication. It is a probe, not a hardened server.

**Windows 11 redirector against it (host, not a guest).** The host's WebClient service was already running (start type Manual with an ETW trigger, `sc qtriggerinfo WebClient`); nothing was installed or reconfigured. Redirector parameters read from `HKLM\SYSTEM\CurrentControlSet\Services\WebClient\Parameters`: `BasicAuthLevel=1`, `FileSizeLimitInBytes=50000000`, `FileAttributesLimitInBytes=1000000`, `SendReceiveTimeoutInSec=60`, `SupportLocking=1`. Server on `127.0.0.1:47080` without authentication, UNC `\\localhost@47080\DavWWWRoot` (log `dav-noauth.log`, user agent `Microsoft-WebDAV-MiniRedir/10.0.26200`):

| Operation | Result |
| --- | --- |
| list root (`Get-ChildItem`) | OK, 0.40 s (OPTIONS, then 4 PROPFIND depth 0/1) |
| read `hello.txt` | OK |
| read 40 000 000 bytes | OK, 2.4 s, 16.1 MB/s |
| read 60 000 000 bytes | **refused by the client** before any GET: "Le dimensioni del file superano il limite consentito" (`ERROR_FILE_TOO_LARGE`); the server saw only PROPFINDs |
| write 40 MB / 60 MB | OK, 9.6 / 9.9 MB/s (sequence: PROPFIND 404, PUT empty, LOCK, PROPPATCH, HEAD, PUT body, PROPPATCH, UNLOCK); the 50 MB limit does not apply to uploads |
| create folder, rename (MOVE), delete, write a text file inside a subfolder | OK |
| Basic authentication over http (`net use \\localhost@47081\DavWWWRoot <pwd> /user:lvm`) | **refused**: system error 67; the redirector sent OPTIONS without credentials, got 401 and gave up (`BasicAuthLevel=1` allows Basic only over HTTPS) |

**Connection pattern:** nearly every request arrives on a **new TCP connection** (new client port per OPTIONS/PROPFIND/GET; a PUT sequence reuses one). This confirms that the redirector cannot be pointed at a `guestfwd` endpoint (section 1): it needs real per-connection TCP.

**Consequences for the design.**

- Per-file read limit 50 MB by default (the 750 MB build case fails); raising it needs `FileSizeLimitInBytes` (up to 4 294 967 295) in the guest registry and a WebClient restart, i.e. administrator rights in the guest (the LightVM Tools installer runs elevated and could set it).
- No HTTP authentication is usable over plain http without lowering `BasicAuthLevel` in the guest. The workable arrangement is the redirector talking to a **WebDAV listener of LightVM Tools on the guest loopback** (`\\localhost@PORT\DavWWWRoot`), which forwards over the authenticated channel to the supervisor; the WebDAV server proper (path confinement, read-only enforcement) runs on the host. The channel, not HTTP, carries the per-VM authentication.
- Throughput of the redirector itself on the host loopback: 10–16 MB/s; inside a guest it adds to the e1000/slirp limit (section 1).
- WebClient start: on Windows 7 and later it is trigger-started; on Vista it is a demand-start service (documentation; not verified here) that the Tools would set to automatic.

**Not verified in a guest:** Vista, Windows 7, Windows 10 guests; XP (its redirector has known restrictions with ports and non-root paths; not verified). The Linux equivalent (davfs2 or a FUSE client in the tools) is not tested. Alternatives if the redirector proves unusable on a guest: a drive provided by the Tools themselves (no inbox file system API for that on XP/Vista without a driver), or synchronised folders (copy in/out by the Tools, no mapping).
